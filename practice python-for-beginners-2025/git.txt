 Задание 3

Чтобы перейти к определенному коммиту, используйте команду git checkout <SHA коммита>. Основная функция git checkout - перемещение указателя HEAD в вашей локальной копии проекта. Указатель HEAD может быть перемещён на любой коммит в истории, либо на любой дрйгой комит из любой ветки. В результате перехода к конкретному коммиту вы оказываетесь в «состоянии отсоединенного указателя HEAD» («detached HEAD state»). В общем, HEAD отклонился от известных веток, так что все изменения с этого момента будут формировать новую последовательность изменений в истории git. При этом git выведет вам напутственное сообщение:«Вы в состоянии detached HEAD. Можете осмотреться, внести какие-нибудь экспериментальные изменения и закоммитить их. Если затем вы переключитесь обратно на ветку, вы сбросите все коммиты, сделанные в этом состоянии, никак не задев никакие ветки».Исходя из этого, у вас есть два варианта:
поэкспериментировать, а затем сбросить все изменения, вернувшись в предыдущую веткупродолжить работу с этого места и начать новую ветку из этой точки.

Для того, чтобы переместить указатель к последнему коммиту в origin воспользуйтесь командой git checkout <имя ветки>, либоб если вы забыли имя ветки и не можете вспомнить, как её посмотреть (git branch), можно использовать команду git checkout -. Команда git checkout HEAD -- <путь до файла> позволяет отменить индексированные изменения для конкретного файла до последнего коммита (на который указывает HEAD). -- означает "рассматривать каждый аргумент после -- как имя файла".

В процессе работы вы можете столкнуться с тем, что в результате ваших экспериментов с git'ом все изменения куда-то пропали. Для решения этой проблемы бывает полезна команда git reflog, которая выводит все промежуточные состояния файлов. Для того, чтобы переключиться на интересующее вас состояние воспользуйтесь командой git reset --hard HEAD@{<порядковый номер из git reflog>}, либо git reset --hard <хэш-идентификатор промежуточного состояния>. Команда git reset --hard <SHA коммита>, может быть применена для перемещения указателя HEAD и указателя Main к необходимому коммиту, затем происходит сброс раздела проиндексированных файлов и рабочего каталога до указанного коммита. Все предыдущие ожидающие изменения в разделе проиндексированных файлов и рабочем каталоге сбрасываются в соответствии с состоянием дерева коммитов. Это значит, что любая работа, находившаяся в состоянии ожидания в разделе проиндексированных файлов и рабочем каталоге, будет потеряна. Таким образом, если команда git checkout HEAD -- <путь до файла> позволяет вам удалить данные об изменениях файлов (перевести файлы из staged в unmodified) и вернуть их в изначальное состояние, то команда git reset --hard позволяет вам удалять добавленные коммиты.На первый взгляд git reset и git checkout очень похожи, однако есть между ними существенное различие:
git reset перемещает указатель HEAD и указатель текущей ветки.git checkout работает исключительно с указателем HEAD; В результате переещения указателя вы получите detached HEAD.

В какой-то момент работы вы захотите не просто отменить все внесённый изменения до последнего коммита (git checkout), а вернуться к определённому коммиту и продолжить работу с него, сохранив при этом всю историю коммитов. Команда git revert <SHA коммита> отменяет действия прошлых коммитов, создавая новый, являющийся копией состояния по указанному хэшу коммита и содержащий все отменённые изменения. Эта команда полезна, когда вы уже запушили изменения в удаленный репозиторий, так как она сохраняет нетронутым исходный коммит.Ещё один полезный приём при работе с git: если в вашей ветке уже было внесено много изменений, а вам необходимо переключиться на другой коммит или другую ветку, вы можете использовать команду git stash save, чтобы быстро сохранить все изменения, а затем при помощи команды git stash pop восстановить эти изменения.Подробнее о работе reset, checkout и revert

 Задание 5

Поскольку на одном проекте могут работать несколько разработчиков, ситуации, когда несколько человек модифицировали один и тот же файл повсеместны, что приводит к конфликтам при объединении (merge) изменений. Зачастую при синхронизации изменений git разрешает конфликты в автоматическом режиме и создаёт соответствующий коммит слияния. Однако вы можете столкнуться с cитуацией, когда git не создал коммит слияния автоматически. Он остановил процесс до тех пор, пока вы не разрешите конфликт. Чтобы в любой момент после появления конфликта увидеть, какие файлы не объединены (Unmerged paths), используйте команду git status 

Всё, где есть неразрешённые конфликты слияния, перечисляется как неслитое. В конфликтующие файлы Git добавляет специальные маркеры конфликтов, чтобы вы могли исправить их вручную. Например, в результате слияния вашей ветки iss53 c веткой master в вашем файле index.html появился раздел, выглядящий примерно так:
 
<<<<<<< HEAD:index.html
Какой-то текст
=======
Какой-то текст
Ещё немного какого-то текста
>>>>>>> iss53:index.html 

Это означает, что версия из HEAD (вашей ветки master, то что вы извлекли из удалённого репозитория для слияния) — это верхняя часть блока (всё, что над =======), а версия из вашей ветки iss53 представлена в нижней части. 
Чтобы разрешить конфликт, придётся выбрать один из вариантов, либо объединить содержимое по-своему. Например, вы можете разрешить конфликт, заменив весь блок следующим:

Какой-то текст
Ещё немного какого-то текста

В этом разрешении есть немного от каждой части, а строки <<<<<<<, ======= и >>>>>>> полностью удалены. 

Разрешив каждый конфликт во всех файлах, запустите git add для каждого файла, чтобы отметить конфликт как решённый. Добавление файла в индекс означает для Git, что все конфликты в нём исправлены.Более подробно о решении конфликтов при слиянии Попробуем разрешить конфликт. Для этого необходимо открыть текстовый файл file_for_conflicts.txt и удалить в нём лишнюю строчку (очевидно какую). 

Я, в свою очередь, внесу свои изменения в этот файл и синхронизирую их с upstream. Таким образом, при попытке выполнить git pull upstream, вы столкнётесь с конфликтом, который не может быть разрешён git в автоматическом режиме. При помощи команды git status проверьте статус файлов, явившихся причиной конфликта. Данный конфликт необходимо разрешить в ручном режиме. Откройте данный файл, разрешите конфликт, оставив только желаемую часть текста и удалив слежебные строки, и зафиксируйте слияние в коммите. Синхронизируйте внесённые вами изменения с вашим origin.
